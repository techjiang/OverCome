做 OverCome 之前，我给自己定了一条硬约束：**整个系统不能有任何运行中的后端进程**。于是很多「理所当然」的功能都得换个思路实现。

## 搜索：最典型的取舍

动态博客的搜索通常是一个 SQL `LIKE` 查询。静态站点没有数据库，常见替代方案有三条路：

| 方案 | 成本 | 体验 |
| --- | --- | --- |
| 接入外部搜索 API（如 Algolia） | 免费额度有限 | 最好 |
| 挂第三方评论/搜索脚本 | 依赖第三方稳定性 | 良 |
| **构建期生成索引 + 前端检索** | 零成本 | 对小站足够 |

我选了第三条。`build.py` 在构建时会把每篇文章的标题、摘要、正文前 600 字写进 `search_index.json`，浏览器端一个手写的高亮检索脚本按关键词打分排序。

对小几百篇文章来说，加载几 KB 的索引做前端过滤，毫秒级返回，体验不比后端差；而成本是 `0`。

## 构建期的「计算权」

架构上一以贯之的原则是：**凡是能在构建期算完的，绝不留到运行时**。

- 目录、阅读时长、相关阅读 → 构建期算好，输出静态 HTML
- 分类、标签、归档页 → 构建期全部生成
- RSS、sitemap → 构建期生成 XML
- 搜索索引 → 构建期导出 JSON

于是线上交付物只剩「一堆文件」，任何静态服务器都能直接托管——这既是 GitHub Pages 能免费承载的原因，也意味着以后迁移到 Cloudflare Pages、Vercel 都只是「换个托管商」而已。

## 收益与边界

收益很实在：

- 爬虫友好，SEO 天然良好
- 页面打开即渲染，无白屏等待
- 没有可攻击的接口面，安全成本趋近于零

边界也要说清楚：前端搜索在数千篇文章、全量正文时性能会下降；评论、访客统计这类强交互功能需要外接服务。如果你的内容规模到了那个量级，说明博客已经成功到需要考虑升级了——那是快乐的烦恼。

```python
# 一个朴素的前端查询评分示例（站点实际实现更完整）
def score(title: str, body: str, keyword: str) -> int:
    s = 0
    if keyword in title:
        s += 10
    if keyword in body:
        s += 1
    return s
```

总而言之：**约束催生简洁**。不依赖任何后端，反而让这套系统在任何时代的任何免费静态托管上都站得住。
